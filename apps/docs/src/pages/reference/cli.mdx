# devsess CLI

The `devsess` binary runs named groups of development services through one detached daemon shared by the current user across projects and worktrees. The CLI requires Node.js on macOS or Linux; running the CLI itself under Bun is not supported. Service commands may use any installed runtime, including Bun.

Install with `npm install -g devsess`, then run `devsess --help`.

## Configuration

By default the CLI reads `$XDG_CONFIG_HOME/devsess/config.json`. When `XDG_CONFIG_HOME` is unset, that is `~/.config/devsess/config.json`. Pass `--config <path>` to use a specific file. The complete file is decoded before a command runs, so unknown or malformed shapes fail early.

The daemon stores its registry and retained logs globally for the user:

| Resource | With XDG variable set | Default |
| --- | --- | --- |
| State directory | `$XDG_STATE_HOME/devsess` | `~/.local/state/devsess` |
| Control socket | `$XDG_RUNTIME_DIR/devsess/devsess.sock` | `/tmp/devsess-<uid>/devsess.sock` |

The state directory contains `running.json` and rotating JSONL logs at `logs/<run-id>/<service-name>.jsonl` plus an optional previous segment at `.1.jsonl`. These locations are shared across worktrees; changing the current directory does not create a separate daemon. Older `.json` log documents are ignored.

The configuration has named projects, each with a path or Git-origin matcher and named presets. A preset is a map of service names to shell commands:

```json
{
	"projects": {
		"acme": {
			"matcher": { "type": "path", "path": "/work/acme" },
			"presets": {
				"web": {
					"awaitPublish": true,
					"services": {
						"frontend": { "command": "bun run dev", "cwd": "apps/web" },
						"api": { "command": "bun run api" },
						"db": { "command": "bun run db", "awaitPublish": false }
					}
				}
			}
		}
	}
}
```

A Git matcher can identify a project by its owner/repository identity, independent of where the checkout lives:

```json
{
	"projects": {
		"devsess": {
			"matcher": { "type": "git", "repo": "fdarian/devsess" },
			"presets": {
				"default": {
					"services": {
						"docs": { "command": "bun run docs" }
					}
				}
			}
		}
	}
}
```

The shorthand `fdarian/devsess` matches normalized remotes such as `git@github.com:fdarian/devsess.git` and `https://github.com/fdarian/devsess`. Project path matchers must be absolute or begin with `~/`. Path matchers use canonical paths and win over Git matchers; among path matches, the longest matching path wins. If equal matches remain, qualify the choice with `--project` (and, when needed, the preset name) instead of relying on config key order.

Service `cwd` is resolved when `start` is invoked. An omitted `cwd` uses the directory from which you invoked the command; a relative `cwd` is relative to that directory; an absolute `cwd` is used as written. The daemon's own working directory does not affect this rule.

Set preset-level `awaitPublish: true` to make `start` wait for each service to call [`publishRunning({ url })`](/reference/devsess). Services that never publish can opt out with `awaitPublish: false` on that service. The default is not to wait. The daemon passes `DEVSESS_SOCKET`, `DEVSESS_RUN_ID`, and `DEVSESS_SERVICE` to each service, including through commands such as `cd apps/web && bun run dev`; `publishRunning` uses them automatically. The running-signal file remains available to `awaitRunning` callers.

## Commands

```text
devsess start [options] [preset]
devsess list [--config path] [--project name]
devsess status [-a|--all] [--project name]
devsess stop [options] [--force] [preset|run-id]
devsess tail [options] [--all-services] [preset|run-id]
devsess attach [options] [preset|run-id]
devsess daemon start
devsess daemon stop [--force]
devsess daemon status
devsess daemon restart [--force]
```

`list` reads the configured file and reports the presets matched by the current directory, including each service command and resolved working directory. It marks presets with `awaitPublish: true`. It does not start the daemon; if a daemon is already reachable, active presets are marked as running. A bare-start summary explains whether `start` would select one preset, show an interactive picker, or fail in a non-interactive invocation.

`status` reports active runs across projects with their short run IDs. Runs under the current directory (or the project named by `--project`) show their start time, uptime, and every service's state, PID, exit code, command, and working directory; other projects get one summary line each. Published services are marked `ready` and show their URL (or named URLs); other published values appear as compact, truncated JSON. The daemon persists readiness with the run and clears it when the service unpublishes or exits. It does not start the daemon. When nothing is running, it shows the most recent finished run from the current directory (or the latest overall) with service exit codes and a `tail` command. If the daemon is down it reports that directly. `-a`/`--all` shows every active run in full detail; finished runs are never listed. If nothing is running, `-a` shows the same `Nothing running` and `Last run` lines as `status`. Use `--project <name>` to narrow the results. `devsess daemon status` instead reports the daemon process itself.

`daemon start` starts the per-user daemon idempotently and reports its PID. `daemon stop` requests a clean shutdown through the daemon; it refuses while services are live unless `--force` is supplied, then waits until the control endpoint is unreachable. `daemon restart` combines those operations. `daemon status` never starts anything: it reports the daemon identity, version, executable, Unix socket, state directory, uptime, and run/client counts. It exits with status `3` when the daemon is not running or not responding, and warns when the daemon differs from the current CLI. The daemon has no TCP port; all control traffic uses the per-user Unix socket shown in the status output. An older daemon that does not support the additive `info`/`shutdown` requests is reported as outdated; stop/restart identifies the process currently owning the socket and verifies its process identity before sending a signal, so stale run records are not used as a kill target.

`start` captures the current environment and starts the selected preset through a detached daemon. It waits for a daemon handshake and for the start request to be acknowledged, then observes the run for about two seconds and prints each readiness publication as it arrives (for example, `frontend ready → http://localhost:5173`). If a service exits during that window it prints its exit status, recent output, and an exact `tail` command; if every service fails, `start` exits nonzero. Otherwise it prints the run ID and returns control to the shell while services continue running. The run records its invocation directory while the daemon and state remain shared across projects and worktrees.

With `awaitPublish: true`, `start` waits until every included service has published; there is no default timeout. After 15 seconds it prints the pending services and a `tail` command for each. If an included service exits without publishing, `start` reports its exit status, recent output, and tail command, then exits nonzero **without stopping the other services**. Press `Ctrl-C` while waiting to stop waiting only; the services keep running and `devsess status` shows their progress.

An active `project/preset` identity cannot be started twice. A completed or failed record may be reused only after every service process has stopped; a record whose aggregate state is failed can still block a duplicate start while one of its services remains live. Use `status` to see the active runs across projects. Preset positionals accept either a bare name or `project/preset`.

Bare `stop`, `tail`, and `attach` consider only runs started under the current directory; they never select a run elsewhere. If none match, the error lists active runs elsewhere with short IDs and shows explicit commands to select one. With a selector, the commands search across projects and prefer active runs. If no active run matches, `tail` replays the most recent matching finished run (under the current directory when no selector was given), while `attach` names its service exit status and gives the exact `tail` command. `stop` still requires an active run. The short run ID shown by `status` works directly as a positional selector, for example `devsess attach c585f251`, `devsess tail c585f251`, or `devsess stop c585f251`; `--run c585f251` also works. Displayed IDs lengthen if needed to avoid collisions. A matching preset name takes precedence over an ID prefix, so use `--run` when both match. A bare preset name still prefers a matching local run. If several active runs match, an interactive terminal offers a preset picker; otherwise the error lists fully qualified commands and short IDs. Use `--project`, a positional `project/preset`, or `--run <id>` to narrow repeated runs. When several services are available, `tail` and `attach` offer a service picker; a run selected outside the current directory is named in its prompt. `--service <name>` (or `-s <name>`) skips it. Non-interactive invocations list exact `--service` commands; `tail --all-services` selects all services explicitly. `attach` requires an interactive terminal to connect. `stop --force` explicitly permits terminating a saved process group whose leader can no longer be verified; it still refuses invalid process-group IDs and can fail if the group does not terminate. If a normal stop cannot verify an orphaned group, the error names the service, run, and PGID and gives both the manual `kill -TERM -<pgid>` command and the `stop --force` remedy. Cancelling any interactive picker with `Ctrl-C` exits with status `130` and restores a new shell line.

`tail` replays retained output and then follows live output from the selected service. For a finished run it announces that it is replaying the last output and returns the saved exit status. An interactive picker also offers all services; `--all-services` selects them without a prompt. When several services are selected, each output chunk is prefixed with `[service-name] `; a chunk can contain several lines, so the prefix is not repeated on every line. A single selected service has no prefix.

Each service writes append-only JSONL and keeps a current segment plus one previous segment, each bounded by the 1 MiB retention budget. Oversized output is split into smaller events before rotation, and replay snapshots the segments at subscription before reading them, so rotation during a replay cannot duplicate or omit events; a partial trailing line from a crash is ignored. Output chunks are coalesced per service, and a bounded producer backlog pauses that PTY until persistence catches up, so control RPCs remain independent of output volume. Client RPC input is backpressured when its bounded queue is full, while lifecycle events use a separate lossless path. Each live connection has a bounded byte writer that waits for socket backpressure without blocking other clients. Replay is streamed under the same drain handling and does not consume the live backlog allowance, so a full retained window can be replayed. If a live writer overflows, it drops unsent output, queues an explicit error frame after the in-flight write even while the socket is draining, waits up to three seconds for that frame to drain, then disconnects. Reconnecting can only replay output still inside the retained segments. A paused tail can hold up to the retained window in daemon memory (about 2 MiB at the default retention; there is no global cap). A slow reader cannot throttle the service: its bounded live buffer eventually overflows, the tail receives an actionable error, and re-running `devsess tail` replays what remains in the retained segments.

`attach` gives one client the service's input lease and prints the keyboard shortcuts when the lease is granted. Press `Ctrl-]` once to detach and return to the shell; press it twice to send a literal `Ctrl-]` to the service. `Ctrl-C` is sent to the service. The detach escape is the single byte `0x1d`: input is parsed byte-by-byte, so a trailing `Ctrl-]` waits up to 250 ms for the next byte, a second `Ctrl-]` is forwarded literally, and any other byte arriving before the timeout is forwarded before detaching. Chunk boundaries do not change these rules, and UTF-8 decoding is stateful across chunks so valid split characters are preserved. This is a text transport, not an arbitrary-byte channel. If the timeout expires first, the attach session detaches and later terminal input is no longer sent to the service. Only one attached input writer is allowed at a time. A disconnected client releases its lease.

`tail` and `attach` use the service's completion status: a normal exit returns its exit code, and signal termination returns `128 + signal` when the exit event includes a signal. Within an active run, tailing an already exited service replays its retained output and then emits its saved exit frame. A persistence failure terminates that service through the normal stop path and completes its tail with exit code `1`. If a daemon restart found the process gone before an exit status was persisted, the frame has no signal and uses exit code `1` to mean “unknown.” When several services are selected, `tail` waits for all of them and returns the first nonzero completion status in completion order (or `0` if all succeed). A zero exit and an explicit attach detach both return `0`; daemon, connection, selection, and live-output-overflow failures are CLI errors with exit status `1`.

## Process ownership and recovery

Services run in their own Unix process groups. The daemon records the process ID, process-group ID, and a birth fingerprint, and verifies all three before signaling a saved process. Live ownership is established only when a newly started PTY's PID is also the process-group leader. A service that exits during identity capture retains its output and exit state without receiving a live ownership handle. If the leader exits while descendants remain, the live ownership handle can signal that group immediately; after the group is observed gone, that handle is permanently invalidated. A recovered record can signal only while its saved leader still matches the saved process-group ID and birth fingerprint. If that leader is gone, a surviving numeric process-group ID is observed but never signaled because it could have been reused; the service is left orphaned instead.

Termination allows up to five seconds after `SIGTERM`, then the same bound after `SIGKILL`, using elapsed-time deadlines rather than a fixed poll count. A recovered run loaded from disk has only a saved identity: a normal stop cannot terminate it unless the daemon can verify the saved leader's identity. If verification fails, the service is marked `orphaned`; `stop --force` can explicitly attempt to terminate the saved PGID. A successful termination reconciles the record and lets the preset start again; a failed recovered attempt remains orphaned, while a failed live stop remains stopping, and both point to the same manual `kill -TERM -<pgid>` or `stop --force` remedy.

Known limitations: if the daemon crashes after spawning a PTY but before persisting its identity, that process may leak. On macOS, `ps lstart` birth fingerprints have one-second precision.
