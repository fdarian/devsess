# devsess CLI

The `devsess` binary runs named groups of development services through one detached daemon shared by the current user across projects and worktrees. The CLI requires Node.js on macOS or Linux; running the CLI itself under Bun is not supported. Service commands may use any installed runtime, including Bun.

Install with `npm install -g devsess`, then run `devsess --help`.

## Configuration

By default the CLI reads `$XDG_CONFIG_HOME/devsess/config.json`. When `XDG_CONFIG_HOME` is unset, that is `~/.config/devsess/config.json`. Pass `--config <path>` to use a specific file. The complete file is decoded before a command runs, so unknown or malformed shapes fail early.

The daemon stores its registry and retained logs globally for the user:

| Resource | With XDG variable set | Default |
| --- | --- | --- |
| State directory | `$XDG_STATE_HOME/devsess` | `~/.local/state/devsess` |
| Control socket | `$XDG_RUNTIME_DIR/devsess/devsess.sock` | `/tmp/devsess-<uid>/devsess.sock` |

The state directory contains `running.json` and `logs/<run-id>/<service-name>.json`. These locations are shared across worktrees; changing the current directory does not create a separate daemon.

The configuration has named projects, each with a path or Git-origin matcher and named presets. A preset is a map of service names to shell commands:

```json
{
	"projects": {
		"acme": {
			"matcher": { "type": "path", "path": "/work/acme" },
			"presets": {
				"web": {
					"services": {
						"frontend": { "command": "bun run dev", "cwd": "apps/web" },
						"api": { "command": "bun run api" }
					}
				}
			}
		}
	}
}
```

A Git matcher can identify a project by its owner/repository identity, independent of where the checkout lives:

```json
{
	"projects": {
		"devsess": {
			"matcher": { "type": "git", "repo": "fdarian/devsess" },
			"presets": {
				"default": {
					"services": {
						"docs": { "command": "bun run docs" }
					}
				}
			}
		}
	}
}
```

The shorthand `fdarian/devsess` matches normalized remotes such as `git@github.com:fdarian/devsess.git` and `https://github.com/fdarian/devsess`. Project path matchers must be absolute or begin with `~/`. Path matchers use canonical paths and win over Git matchers; among path matches, the longest matching path wins. If equal matches remain, qualify the choice with `--project` (and, when needed, the preset name) instead of relying on config key order.

Service `cwd` is resolved when `start` is invoked. An omitted `cwd` uses the directory from which you invoked the command; a relative `cwd` is relative to that directory; an absolute `cwd` is used as written. The daemon's own working directory does not affect this rule.

## Commands

```text
devsess start [options] [preset]
devsess list
devsess stop [options] [--force] [preset]
devsess tail [options] [preset]
devsess attach [options] [preset]
```

`start` captures the current environment and starts the selected preset through a detached daemon. It waits for a daemon handshake and for the start request to be acknowledged, prints the run ID, and returns control to the shell while services continue running. The run records its invocation directory while the daemon and state remain shared across projects and worktrees.

An active `project/preset` identity cannot be started twice. A completed or failed record may be reused only after every service process has stopped; a record whose aggregate state is failed can still block a duplicate start while one of its services remains live. Use `list` to see active runs in the current project first, followed by runs elsewhere for the same daemon.

`stop` selects a run in the current project. If more than one running preset matches, give its preset name. `stop --force` explicitly permits terminating a saved process group whose leader can no longer be verified; it still refuses invalid process-group IDs and can fail if the group does not terminate. If a normal stop cannot verify an orphaned group, the error names the service, run, and PGID and gives both the manual `kill -TERM -<pgid>` command and the `stop --force` remedy. `attach` requires `--service <name>` when the preset has multiple services. These commands report ambiguity instead of silently choosing a run or attachment target.

`tail` replays retained output and then follows live output from every service in the selected preset. Use `--service <name>` to select one service. When several services are selected, each output chunk is prefixed with `[service-name] `; a chunk can contain several lines, so the prefix is not repeated on every line. A single selected service has no prefix.

Each service retains at most 1 MiB of UTF-8 log data. Oversized output is split into smaller events before retention, and older events are discarded to keep the retained window within the limit. Live subscribers use a bounded queue of 256 events and wait for socket backpressure to drain. If a subscriber exceeds the event or socket buffer bound, it receives an explicit error frame before the connection closes. Reconnecting can only replay output still inside the retained window.

`attach` gives one client the service's input lease and prints the keyboard shortcuts when the lease is granted. Press `Ctrl-]` once to detach and return to the shell; press it twice to send a literal `Ctrl-]` to the service. `Ctrl-C` is sent to the service. The detach escape is the single byte `0x1d`: input is parsed byte-by-byte, so a trailing `Ctrl-]` waits up to 250 ms for the next byte, a second `Ctrl-]` is forwarded literally, and any other byte arriving before the timeout is forwarded before detaching. Chunk boundaries do not change these rules, and UTF-8 decoding is stateful across chunks so valid split characters are preserved. This is a text transport, not an arbitrary-byte channel. If the timeout expires first, the attach session detaches and later terminal input is no longer sent to the service. Only one attached input writer is allowed at a time. A disconnected client releases its lease.

`tail` and `attach` use the service's completion status: a normal exit returns its exit code, and signal termination returns `128 + signal` when the exit event includes a signal. Tailing an already exited service replays its retained output and then emits its saved exit frame. When several services are selected, `tail` waits for all of them and returns the first nonzero completion status in completion order (or `0` if all succeed). A zero exit and an explicit attach detach both return `0`; daemon, connection, and selection failures remain CLI errors.

## Process ownership and recovery

Services run in their own Unix process groups. The daemon records the process ID, process-group ID, and a birth fingerprint, and verifies all three before signaling a saved process. Live ownership is established only when a newly started PTY's PID is also the process-group leader. A service that exits during identity capture retains its output and exit state without receiving a live ownership handle. If the leader exits while descendants remain, the live ownership handle can signal that group immediately; after the group is observed gone, that handle is permanently invalidated. A recovered record can signal only while its saved leader still matches the saved process-group ID and birth fingerprint. If that leader is gone, a surviving numeric process-group ID is observed but never signaled because it could have been reused; the service is left orphaned instead.

Termination polls up to 200 times at 25 ms intervals (5 seconds) after `SIGTERM`, then allows the same 5-second bound after `SIGKILL`. A recovered run loaded from disk has only a saved identity: a normal stop cannot terminate it unless the daemon can verify the saved leader's identity. If verification fails, the service is marked `orphaned`; `stop --force` can explicitly terminate the saved PGID, after which the record is reconciled and the preset can start again. Until then, duplicate starts remain blocked and point to the same manual `kill -TERM -<pgid>` or `stop --force` remedy.

Known limitations: if the daemon crashes after spawning a PTY but before persisting its identity, that process may leak. On macOS, `ps lstart` birth fingerprints have one-second precision.
