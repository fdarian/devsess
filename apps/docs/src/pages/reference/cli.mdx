# devsess CLI

The `devsess` binary runs named groups of development services in a detached, per-worktree daemon. Install the package, then make the binary available with `bunx devsess ...` or the equivalent package-manager command.

## Configuration

By default the CLI reads `$XDG_CONFIG_HOME/devsess/config.json`. When `XDG_CONFIG_HOME` is unset, that is `~/.config/devsess/config.json`. Pass `--config <path>` to use a specific file. The complete file is decoded before a command runs, so unknown or malformed shapes fail early.

The configuration has named projects, each with a path or Git-origin matcher and named presets. A preset is a map of service names to shell commands:

```json
{
	"projects": {
		"acme": {
			"matcher": { "type": "path", "path": "/work/acme" },
			"presets": {
				"web": {
					"services": {
						"frontend": { "command": "bun run dev", "cwd": "apps/web" },
						"api": { "command": "bun run api" }
					}
				}
			}
		}
	}
}
```

Project path matchers must be absolute or begin with `~/`. Path matchers use canonical paths and win over Git matchers; among path matches, the longest matching path wins. Equivalent SSH and HTTPS Git origins are normalized before comparison. If equal matches remain, qualify the choice with `--project` (and, when needed, the preset name) instead of relying on config key order.

Service `cwd` is resolved when `start` is invoked. An omitted `cwd` uses the directory from which you invoked the command; a relative `cwd` is relative to that directory; an absolute `cwd` is used as written. The daemon's own working directory does not affect this rule.

## Commands

```text
devsess start [options] [preset]
devsess list
devsess stop [options] [preset]
devsess tail [options] [preset]
devsess attach [options] [preset]
```

`start` captures the current environment and starts the selected preset through a detached daemon. It waits for a daemon handshake and for the start request to be acknowledged, prints the run ID, and returns control to the shell while services continue running. The daemon is scoped to the canonical current directory, so separate worktrees have separate daemons and state.

An active `project/preset` identity cannot be started twice. A completed or failed record may be reused only after every service process has stopped; a record whose aggregate state is failed can still block a duplicate start while one of its services remains live. Use `list` to see active runs in the current project first, followed by runs elsewhere for the same daemon.

`stop` selects a run in the current project. If more than one running preset matches, give its preset name; `--service <name>` is required for `tail` and `attach` when the preset has multiple services. These commands report ambiguity instead of silently choosing a service.

`tail` replays retained output and then follows live output. Each service retains at most 1 MiB of UTF-8 log data; a single event is retained even if it exceeds that size. Live subscribers use a dropping queue of 256 events, and an oversized (over 1 MiB) protocol frame closes the connection. Reconnecting can only replay output still inside the retained window.

`attach` gives one client the service's input lease. Press `Ctrl-]` to detach and return to the shell; `Ctrl-C` is sent to the service. Only one attached input writer is allowed at a time. A disconnected client releases its lease.

## Process ownership and recovery

Services run in their own Unix process groups. The daemon records the process ID, process-group ID, and a birth fingerprint, and verifies all three before signaling a saved process. A newly started PTY is accepted only when its PID is also the process-group leader. If the leader exits while descendants remain, the live ownership handle can signal that group immediately; after the group is observed gone, that handle is permanently invalidated to avoid PID/PGID reuse.

Termination polls up to 200 times at 25 ms intervals (5 seconds) after `SIGTERM`, then allows the same 5-second bound after `SIGKILL`. A recovered run loaded from disk has only a saved identity: it cannot be terminated unless the daemon can verify that the same process group still exists. If verification fails, the service is marked `orphaned` and the run remains blocked from duplicate starts until the stale record is dealt with.
